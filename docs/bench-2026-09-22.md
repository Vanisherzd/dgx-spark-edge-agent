# Inference benchmark on the DGX Spark (2026-09-22)

Goal: pick the model + acceleration for the edge agent's small-RAG / tool-calling workload. Hardware limit: LPDDR5x
~273 GB/s, so single-stream decode ≈ bandwidth ÷ bytes of weights read per token. Method: `scripts/try.sh` per config
(fresh server on :8101, `--max-model-len 32768 --max-num-seqs 8`), `scripts/bench.py` (256-token answers, 12.9k-token
runbook prompt), `scripts/probe.py` (8 needle questions with exact answers), `scripts/smoke.py` (tool call parsed).
Raw log: `logs/matrix.log`, `logs/probe.log`; table via `scripts/bench-summary.py logs/matrix.log`.

## Findings

- **KV cache FP8** (`--kv-cache-dtype fp8`): capacity only (+12 % on the hybrid 27B, +70 % on the 35B), decode speed
  unchanged. Decode here is weight-bandwidth bound; KV bandwidth only matters at much longer contexts or higher
  concurrency. Not enabled by default (584k tokens of BF16 KV is already plenty for 8 sequences); flip it on when RAG
  contexts get long.
- **MTP** (in-checkpoint multi-token prediction, `{"method":"mtp"}`): the big win. 27B ×2.1, 35B ×1.36 single
  stream; aggregate throughput also up. Output quality unchanged on the probe.
- **DFlash / DFlash2** external drafters: DFlash2 gave the 27B its best single-stream number (×2.8) but z-lab DFlash on
  the 35B was worse than MTP everywhere and halved concurrent throughput (15 draft tokens per step). Both cost 3–4 GB
  of KV budget and 2–4 extra minutes of startup.
- **Model choice**: the MoE (35B total, 3B active, FP8) reads ~3.5 GB of weights per token vs ~21 GB for the dense
  27B NVFP4, hence ~4× the base decode speed, and it matched the dense model on the needle probe. Its free-form
  long answers are wordier and once mislabeled a detail (`php9-fpm` under runbook 3) that the 27B got right, so
  keep answers constrained (tool calls / JSON / short fields) for decisions.
- **Prefix caching** works: the 12.9k-token runbook prompt costs 3.5–5.6 s cold and ~0.25 s on a hit. For a small
  RAG corpus, putting the whole corpus in the system prompt is viable.

## Decision

Production default (`scripts/serve.sh`): `Qwen/Qwen3.6-35B-A3B-FP8`, `--speculative-config
{"method":"mtp","num_speculative_tokens":3}`, `--tool-call-parser qwen3_coder --reasoning-parser qwen3`,
`--max-num-seqs 8`, `--gpu-memory-utilization 0.45` (~54 GiB; leaves ~60 GiB for embeddings / RAG / OS).
Fallbacks by env: `MODEL=unsloth/Qwen3.8-27B-NVFP4 TOOL_PARSER=qwen3_xml SPEC='{"method":"mtp","num_speculative_tokens":5}'`
for the precision-first dense model; `MODEL=Qwen/Qwen3-8B TOOL_PARSER=hermes SPEC=` for the old small model.

## Incident during this run

First-time FlashInfer JIT for `sm_121a` with default ninja parallelism (65 compiler processes observed) exhausted the
119 GiB unified memory (no swap): kernel OOM-killer 02:39–02:50, load 177, sshd/kubelet/ollama unresponsive for
~2.5 h. Recovered without reboot by killing the compilers over a very slow SSH login. Fixes now in the scripts:
`MAX_JOBS=4 FLASHINFER_NVCC_THREADS=4`, `logs/watchdog.sh` (kills compilers + vLLM if MemAvailable < 12 GiB during
experiments), compiled ops persist in `~/.cache/flashinfer/0.6.18/121a/`.
